# 思想到执行器的适配图

本 Skill 不规定具体框架。下面只说明某类问题需要什么能力，以及常见工具家族可以提供什么。

## 选择原则

先回答四个问题：

1. 主要未知量是输入、操作历史、并发调度、环境故障还是用户交互？
2. Oracle 能否自动执行？
3. 失败能否保存并缩减？
4. 现有项目已经有哪些测试、日志、Mock、模拟器和故障钩子？

优先复用现有设施。不要为了使用某个流行工具重写系统。

## 适配表

| 测试思想 | 执行器需要具备 | 常见家族示例 | 不能替代什么 |
|---|---|---|---|
| 章程式探索 | 记录路径、笔记、时间箱、可追踪发现 | 人工会话、浏览器代理、设备操作脚本 | 风险模型、回归沉淀 |
| 错误猜测 | 历史缺陷、错误分类、实现知识 | Checklist、故障分类表、评审工作坊 | 系统覆盖证明 |
| 属性测试 | 生成有效域、关系断言、缩减、Seed | QuickCheck/Hypothesis/fast-check/proptest 等 | 完整业务 Oracle |
| 覆盖引导 Fuzz | Harness、覆盖反馈、Corpus、崩溃保存 | libFuzzer、AFL++、LibAFL、Atheris 等 | 状态机和业务语义 |
| 状态/模型测试 | 命令生成、参考模型、操作历史、缩减 | Stateful PBT、模型测试、确定性模拟 | 真实依赖故障 |
| API 模糊测试 | Schema、请求变异、状态链、响应 Oracle | OpenAPI/GraphQL/协议 Fuzzer | 业务侧独立核对 |
| UI Monkey | 事件生成、Seed、范围控制、状态快照 | ADB Monkey、浏览器/桌面事件生成器 | 配置完整性和业务 Oracle |
| 故障注入 | 稳态、故障钩子、落地证据、回滚、终止条件 | 网络代理、tc、进程控制、资源压力、Chaos 平台 | 数据模型检查器 |
| 长稳/压力 | 长时运行、资源趋势、阈值、恢复观察 | Soak、load、stress、profiling | 功能正确性 |
| Mutation | 故意改变实现或断言并统计是否被杀死 | Mutation 工具、人工故障植入 | 产品运行时测试 |

## 适配器接口建议

无论底层工具是什么，尽量对外暴露统一概念：

```text
prepare_baseline()
apply_perturbation(scenario)
prove_perturbation_landed()
execute_workload(seed, history)
collect_observations()
run_oracles()
restore_environment()
export_reproducer()
```

这不是要求统一代码接口，而是统一测试活动的证据链。

## Fuzz 的通用思想

从覆盖引导 Fuzz Skills 中吸收：

- Harness 必须快、确定、可重复；
- 每次执行隔离或重置状态；
- 从真实有效样本建立 Corpus；
- 结构化输入使用字典、生成器或结构感知变异；
- 保存崩溃、Hang、Seed 和最小输入；
- 覆盖增长是导航信号，不是正确性 Oracle；
- Sanitizer、Core 和独立断言共同增强发现能力。

不要把这些原则限制在 C/C++：任何自动生成器都需要确定性、可保存、可缩减和强 Oracle。

## 模型驱动序列的通用思想

对外部可观察操作建立简化模型：

```text
模型状态 + 可执行命令 + 命令前置条件 + 模型更新 + 真实系统检查
```

生成器负责组合操作历史，缩减器负责把失败历史缩短。适用于：

- 生命周期 API；
- 连接、断开、重连；
- 创建、更新、删除、恢复；
- 消息发布、确认、重试；
- 权限变化；
- 多页面或多客户端操作。

## Chaos 的通用思想

- 先定义稳态和假设；
- 从小范围、可逆故障开始；
- 为故障设置持续时间、停止条件和回滚；
- 证明故障真正作用到目标；
- 检查数据和恢复，不只看监控曲线；
- 修复后重新注入同一故障；
- 生产执行需要明确授权和最小爆炸半径。

## Mutation 的通用思想

Mutation 回答的是：“现有测试真的能识别错误实现吗？”

高价值做法：

- 翻转条件；
- 删除校验；
- 取消错误处理；
- 移除去重或锁；
- 改变边界比较；
- 让函数返回固定成功；
- 跳过持久化或恢复步骤。

若测试仍然全绿，说明断言或场景没有约束对应声明。
