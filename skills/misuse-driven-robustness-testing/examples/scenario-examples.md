# 场景讨论示例

这些示例展示如何使用同一思想跨越不同系统。它们不是固定用例，也不是要求使用对应工具。

## 示例一：嵌入式 Wi-Fi 生命周期

### 正常流程

```text
init → bind_ifname → enable → scan → disable
```

### 声明

- C1：未绑定接口时 `enable` 必须明确失败，且不创建后台线程；
- C2：重复 `scan` 不会无限扩张队列或并发启动扫描；
- C3：`disable` 返回后，旧扫描结果不能写入新一代对象；
- C4：连接状态变化不会自动篡改 Network 的 IP 策略。

### 讨论点

正常测试通常只验证一条正确路径。误用驱动测试会生成：

```text
enable
bind_ifname
scan
scan
disable
旧 scan-result 事件到达
bind_ifname(new)
enable
```

但不要一上来把所有动作放在一个测试。拆成：

1. 未绑定直接 enable；
2. RUNNING 中重复 scan；
3. scan 与 disable 并发；
4. disable 后旧事件到达；
5. 对象重建后旧回调持有陈旧引用。

### Oracle

- 线程、Socket、队列和对象世代快照；
- 状态机查询；
- ASan/UBSan/Core；
- 事件序号与对象 generation；
- 下一次合法 enable 是否成功。

“没有崩”不能证明 C3。必须证明旧事件没有污染新对象。

## 示例二：配置写入时掉电

### 声明

C1：配置更新要么完整采用新值，要么保留旧值，不能出现半文件或字段混搭。

### 分解

将更新流程分成阶段：

```text
读取旧配置 → 生成新内容 → 写临时文件 → fsync → rename → 目录 fsync → 加载
```

在每个阶段注入终止或掉电模拟，重启后检查：

- 配置可解析；
- 只有旧版本或新版本；
- 临时文件可清理；
- 不会因为损坏配置进入无限重启；
- 错误可诊断并可恢复。

### 讨论点

仅测试“写入失败返回错误”不够。真正的声明是**跨进程崩溃和重启后的原子性**。

## 示例三：事件中继与回调重入

### 声明

- C1：中继调用回调时不持有会导致重入死锁的内部锁；
- C2：订阅取消后，旧回调不会访问已释放模块；
- C3：事件突发时 mailbox 有界，超载策略明确；
- C4：重复事件不会产生重复业务效果。

### 误用场景

- 回调中再次注册或取消订阅；
- 回调中调用另一个会产生事件的公共 API；
- 一个线程取消订阅，另一个线程正准备分发；
- 同一事件重复 1、2、1000 次；
- mailbox 满时再到达高优先级事件；
- 模块销毁后延迟事件到达。

### Oracle

- 锁依赖检测或 watchdog；
- 对象 generation 与引用计数；
- mailbox 水位；
- 业务效果计数；
- 丢弃/合并策略日志。

## 示例四：支付或创建订单 API

### 正常路径

```text
客户端提交 → 服务端扣款 → 写订单 → 返回确认
```

### 关键声明

C1：相同幂等键的重试最多产生一个业务效果。

### 高价值误用

- 服务端已扣款，但响应在网络中丢失；
- 客户端超时后立即重试；
- 两个并发请求使用相同幂等键；
- 相同幂等键携带不同订单内容；
- 第一次请求处于“结果未知”时服务重启；
- 回调重复投递。

### Oracle

不能只检查 HTTP 200。需要独立核对：

- 账务效果数量；
- 订单数量；
- 幂等记录；
- 返回结果一致性；
- 未知结果的重试语义；
- 对账与恢复后的最终状态。

## 示例五：GUI / Android Monkey

随机事件生成器可以产生大量点击、返回、旋转和切换，但它本身没有产品 Oracle。

### 不合格活动

```text
运行 100000 个事件；应用没崩；结论：PASS
```

### 合格活动

先定义声明：

- C1：关键流程中任何返回/切后台都不能造成重复提交；
- C2：设置页任意乱点后，持久化配置仍可解析；
- C3：权限被拒绝或中途撤销时应用不泄漏资源；
- C4：事件活动结束后应用可回到首页并继续正常操作。

再为随机活动增加：

- 固定 Seed；
- 事件范围与禁区；
- 周期性状态快照；
- 崩溃、ANR、资源、持久化与业务效果 Oracle；
- 最后执行确定性健康检查；
- 出错时保存最短事件序列，而非只保存整段日志。

## 示例六：不会操作的真实用户

某设置包含“自动获取地址”和“手动地址”，用户可能：

1. 开启手动模式但不填网关；
2. 保存后立刻切回自动；
3. 在连接尚未完成时再次保存；
4. 看到超时就连续点击保存；
5. 退出页面后以为设置已生效；
6. 重启设备发现网络不可用。

讨论焦点不应是“用户为什么乱点”，而是：

- UI 是否表达当前阶段；
- 无效组合是否被拒绝；
- 保存是否原子；
- 重复提交是否合并；
- 失败是否保留上一个可用配置；
- 用户是否能恢复而不需要工程师介入。
