# 尖锐质询(interrogation)

任务收尾的最后一道闸:**执行者汇报"做完了"之前**,必须先过一遍质询。
质询者不是执行者自己,而是一个**全新无上下文代理**——它没听过执行者的
叙述,只信仓库里可复核的东西,所以执行者的自嗨在这里骗不过去。

## 流程(执行者侧,汇报前自动跑)

1. **spawn 质询代理**(task 工具,只读):把本 skill 全文 + 改动范围
   (分支 / diff 基点 / 涉及文件)交给一个全新代理。不要把会话上下文
   转交给它——"无上下文"是质询有效的前提。
2. **质询代理产出问题清单**(指令见下节),交回执行者。
3. **执行者逐条回答**(义务见下节),出质询记录。
4. **汇报里附质询记录**(成立质疑的整改结果 + 被驳回质疑的理由)。
   没有质询记录的"完成汇报"不算完成。

琐碎改动(纯文案笔误、单行格式化、重命名)可豁免并一句话说明;豁免
判断失当的代价是:评审发现的问题本该在质询里被拦下。

## 质询代理指令(spawn 时原样转交)

你是一个刚被拉进来的审讯者,没有参与之前的任何讨论。你的任务是向
执行者提出尖锐问题,不是配合,不是夸奖。规则:

1. **先自己看**:读本次改动的 diff 与受影响的调用点(grep 所有被改
   公共函数的调用方),不要问能自己查到的问题。
2. **问题必须尖锐且可证伪**,围绕五个轴,每个轴至少一问:
   - **依据**:这个改动的依据是什么?是协议/规范/仓库既有实现,
     还是执行者自己发明的?"既有实现"要给出文件行号。
   - **验证**:验证覆盖了哪条路径?没覆盖哪条?验证结果证明的是
     "行为对"还是只是"没报错"?有没有只测了 Happy path?
   - **过度设计**:是否存在一个函数能搞定却写了一堆状态机/抽象层
     的情况?diff 行数与解决的问题相称吗?有没有为"以后可能"
     而写的代码?
   - **传染性**:下一个 AI/人看到这段代码,会照着它写出什么?
     这次的写法是收敛的(后人只能走正路)还是示范了坏样板
     (后人会复制)?
   - **安全**:拒绝路径有没有副作用?坏值能不能落到盘上/发到网上?
     输入在信任边界上验了吗?
3. **故意夹带 1~2 条不成立的质疑**(听起来专业但实际站不住,如
   指控没发生的事、把正确行为说成 bug)。执行者能识破才算合格。
4. 输出格式:编号问题清单,每条 ≤3 行,标注轴名。不写总评——总评
   留给执行者的回答之后。

## 执行者义务(收到问题清单后)

- 逐条回答,每条以【事实】或【扯淡】开头:
  - 【事实】→ 给证据(文件:行号 / 命令输出 / 文档条目)并整改;
  - 【扯淡】→ 指出质疑错在哪,同样要证据;反驳成立的前提是可复核。
- 不允许"你说的有道理我回去看看"式拖延:当场定性,当场给证据。
- 全部回答完,输出质询记录:改动概要 / 成立的质疑与整改 / 被驳回的
  质疑与理由 / 遗留风险。随汇报交付,或贴 MR 描述。

## 边界

- 质询不改变技术决策权:用户仍是最终拍板人。
- 质询代理只读不写,不直接改代码;整改由执行者做。
- 质疑若全部被驳回且证据确凿,记录"通过,无整改项"即可,不强行找茬。
