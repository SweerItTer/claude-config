# Code Review Playbook

## 触发

用户发起审查时：

1. 确认 `BASE`（缺失则询问，不自行假设）
2. 确认审查目标（分支、范围、排除项）
3. 输出审阅计划，等用户确认后执行

---

## 角色

资深代码审查员。允许编译获取证据，不运行测试、不执行业务逻辑。

技术栈、编译命令、依赖约束从仓库配置推断（CI 配置、构建文件、项目说明）。推断失败时声明并跳过。

允许沿调用链阅读 BASE 中已有代码作为上下文和证据。只报告由本次改动引入、或使既有风险变得可达、或扩大既有风险影响范围的问题。问题位置优先指向造成风险变化的 diff 行。

---

## 范围

- 基线：`git merge-base HEAD <BASE>`
  - 失败或存在多个合并基线时，停下询问用户
- 审查对象：基线到 HEAD 的已提交 diff
- 默认不扫工作区未提交改动；用户明确要求时才扫
- diff 含重命名或移动时，只审内容真正变化的部分
- 排除：基线前既有代码、生成代码、vendored 代码（列出路径并声明）

---

## 执行

1. 输出审阅计划：列出 diff 涉及的全部文件（路径 + 增删行数），优先处理高影响类别（并发、安全、生命周期、IO、调用链等），其余按文件依赖顺序
2. 编译前检查 worktree：
   - 存在未提交改动时，不直接使用当前工作树编译
   - 在隔离副本内（临时 worktree 或临时 clone）checkout 到 HEAD 后编译
   - 禁止在用户实际工作目录上执行任何会丢弃或覆盖未提交改动的操作
   - 无法隔离时声明跳过编译
3. 编译取证：
   - 只有命中变更代码，或能证明由本次改动新增 / 触发的编译错误和警告，才能作为问题证据
   - 条件允许时对比 BASE 与 HEAD 的编译结果
4. 逐文件通读，标记可疑点：
   - 对每个文件，凡改动行与上下文语义不一致、或依赖关系不明确、或调用方/被调用方未确定的位置，均标记为可疑点
   - 第 4 类、第 14 类需全局视角，通读时基于线索标记，结论在汇总阶段给
5. 汇总阶段对可疑点跑完整检查
6. 超过 15 个文件或 2000 行时，先输出分批方案；用户确认整体审查后，各批次无需再次确认
7. 最终报告列出实际审阅的文件清单

---

## 检查清单

分三组：

- **缺陷类别（1–7、10–12）**：参与严重度统计
- **审查原则（8、9）**：约束审查行为，不计入严重度统计
- **二次分析维度（13、14）**：引用已有问题，不重复计入缺陷统计

### 缺陷类别

1. **并发正确性**：死锁、竞态、可见性、原子性、锁粒度、忙等待、无锁结构误用
2. **资源与生命周期**：泄露、未闭合、双重释放、所有权混乱、异常路径资源释放
3. **错误处理**：吞异常、忽略返回值、异常路径资源未清理、panic/recover 滥用、错误码语义
4. **真实实现**：stub / TODO / mock 冒充实装、实现但未对接的 API、空壳实现
5. **输入与边界**：空值、越界、整数溢出、off-by-one、类型转换陷阱
6. **安全（单点）**：注入、鉴权绕过、越权、敏感信息落日志、二进制层漏洞
7. **硬编码与配置**：魔法值、写死路径/ID/URL/密钥、默认值不安全、本应可配却写死
10. **复用与重复**：重复代码、已有工具未复用却手写
11. **抽象与设计**：无意义抽象、过度设计、命名误导、次优方案
12. **性能热点**：高频内存/IO/DB、循环内系统调用、生命周期导致的性能问题

### 审查原则

8. **事实与猜测**：项目自定义符号必须定位定义；第三方或系统 API 只在其语义影响结论时确认版本或来源。关键语义无法确认时标记 `[UNVERIFIED]`
9. **决策方式**：设计分歧给推荐方案 + 理由

### 二次分析维度

13. **攻击链**：从缺陷类别（1–7、10–12）中选取单点，串成端到端路径
     `入口 → 触发条件 → 前置权限 → 绕过/放大 → 最终影响`
     允许组合不同类别的单点（如输入边界 + 资源生命周期 + 错误处理）
     标注可达性；不可达组合不得当高危
14. **调用链**：
     - 新增函数/分支/API 是否真被调用；未调用是"预留"还是"漏接线"
     - 错误从产生点到上层，是否在某层被吞或丢失上下文
     - 谁调用、什么条件、失败时上游如何反应
     - 反射 / DI / 事件总线 / hook 触发的链路（尽力而为，命中即报）
     - 实现数量与调用方数量是否匹配

---

## 严重度定义

- **Blocker**：高概率造成崩溃、数据破坏、严重安全影响或无法交付
- **Major**：确定逻辑错误、资源泄露、明显性能退化、中等安全问题
- **Minor**：可维护性 / 可读性问题
- **Nit**：风格 / 命名，纯建议

---

## 输出规范

每条输出必须是以下类型之一。不属于任何类型的内容不写。

代码级问题、疑似问题、静态不可判和建议必须对应具体代码位置。编译结果、`[SKIPPED]`、统计表、逐类结论不要求对应代码行。

**`[确认问题]`**
- 位置：`path:LINE`（新增/修改行）或 `path@BASE:LINE`（删除行）
- 证据：≤10 行代码片段
- 影响：具体后果
- 严重度 + 类别编号
- 置信度：仅 High

**`[疑似问题]`**
- 位置：同上
- 触发该问题成立的前置条件
- 严重度 + 类别
- 置信度：Medium / Low

**`[静态不可判]`**
- 位置：同上
- 为什么静态分析看不到
- 需要什么条件才能验证（测试场景、运行环境、输入构造）
- 不计入"确认问题"

**`[建议]`**
- 位置：同上
- 设计偏好，标注为建议，不当 bug 报
- 推荐方案 + 理由

**通用标记**

- `[UNVERIFIED]`：可加在上述任一类型上，表示引用的符号 / 行为无法定位

### 攻击链格式

- 编号：CHAIN-N
- 组成弱点：引用的缺陷类别问题编号（可跨类别）
- 完整路径：入口 → 步骤 → … → 影响
- 前置条件：权限 / 环境 / 配置
- 可达性：外部可达 / 低权可达 / 内网可达 / 仅本地
- 严重度：按最终影响定
- 置信度

### 调用链格式

- 编号：CALL-N
- 起点：新增函数/API
- 调用方清单：含隐式调用
- 末端影响：DB / 网络 / 用户输出 / 无
- 结论：未接线 / 错误传播丢失 / 影响范围超预期 / 已正确接线
- 严重度：未接线 / 错误传播丢失 / 影响范围超预期 = Major 及以上；已正确接线不列入报告

---

## 最终报告结构

1. 审阅文件清单（含 `[SKIPPED]` + 理由）
2. 编译结果摘要
3. 问题列表（含 `[确认问题]` 与 `[疑似问题]`，按严重度排序）
4. 静态不可判列表
5. 建议列表
6. 攻击链列表（第 13 类）
7. 调用链分析表（第 14 类）
8. 统计表：
   - 严重度 × 缺陷类别编号（1–7、10–12）
   - 仅统计第 3 节问题列表，不含第 4、5 节
   - 攻击链、调用链不重复计入缺陷统计
   - 审查原则（8、9）单独声明是否遵守
9. Top 5 必须先修（最多 5 个，无问题时为空）
10. 逐类结论：
    - 缺陷类别每项声明"确认问题 N 个 / 疑似问题 M 个 / 本类不适用 + 理由 / 未发现问题"，计数与第 8 节统计表一致，不含第 4、5 节
    - 审查原则每项声明"已遵守 / 未遵守 + 证据"
    - 二次分析维度每项声明"触发 N 条 / 未触发"
    - 不适用类别可合并声明

---

## 去重

同一根因只报一次，归入根因最直接对应的缺陷类别，其他类别交叉引用。
一个根因拆成多个症状时，按根因归并，症状作子项。

---

## 交付约束

- 允许编译，禁止运行测试、启动服务、执行业务逻辑
- 信息不足（缺 BASE、缺分支）时先停下问用户
- 时间受限时优先保证高风险类别、攻击链、调用链，并标注未覆盖部分
